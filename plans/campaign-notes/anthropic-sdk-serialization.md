# LOOK INTO DATA SERIALIZATION WITH THE ANTHROPIC SDK

Gluck, 2026-08-19: "leave a note somewhere to look into data serialization
with the anthropic sdk, there must be a better way to use it but perhaps not."

Written by 223a0986 at the point where the question was parked, with what was
MEASURED rather than what was assumed, so the next person starts from evidence.

## WHAT IS ALREADY KNOWN, WITH THE INSTRUMENT THAT SHOWS IT

    THE ROUND TRIP IS LOSSLESS. anthropic.MessageParam has both MarshalJSON
    and UnmarshalJSON, and marshal -> unmarshal -> marshal is BYTE-IDENTICAL
    across text, thinking WITH ITS SIGNATURE, redacted thinking, tool_use,
    tool_result and a mixed block list.
    (TestMessageParamRoundTripsThroughJSONWithoutLoss, anthropicsdk.)

    THERE IS NO PROTO. anthropic-sdk-go v1.42.0 carries no .proto anywhere in
    the module; it is a REST/JSON SDK generated by stainless.

    THE PARSE IS THE WHOLE COST, AND IT IS LARGE. Turning stored rows into
    typed MessageParam, measured at three sizes, exactly linear:

        1,000 messages     73,001 allocs    5.87 MB    10.5 ms
       10,000 messages    730,003 allocs   58.7 MB      110 ms
       50,000 messages  3,650,002 allocs  293.6 MB      490 ms

    73 allocations and 5.87 KB PER MESSAGE. The raw provider's whole-history
    read is 2 allocations, constant, 32.768 bytes per message, because it
    hands stored bytes to the wire and never builds an object graph.

    IN THE LIVE PATH: a steady-state send on the SDK provider costs 11.2-11.4
    ms at 1,000 messages against 45-66 us on the raw provider. Same work, same
    conversation, ~200x.

## THE LEVER THAT EXISTS AND WAS NOT TAKEN

`option.WithRequestBody(contentType, body)` accepts `[]byte` or an io.Reader
and sets the request body directly, so the SDK can be handed a PRE-MARSHALLED
request and never build typed messages at all.

AND RETRIES SURVIVE IT, which was the first thing to doubt: a `[]byte` becomes
a `*bytes.Buffer`, requestconfig's `*bytes.Buffer` case sets ContentLength AND
GetBody, and `shouldRetry` refuses only when `req.Body != nil && req.GetBody ==
nil`. So the retry path is intact with a custom body. (Read in
internal/requestconfig/requestconfig.go at v1.42.0, lines 394-410 and 245-256.)

## WHY IT WAS NOT TAKEN, WHICH IS THE REAL QUESTION FOR NEXT TIME

The typed messages are not only carried; they are TRANSFORMED. buildParams
coalesces adjacent same-role messages, marks prompt-cache breakpoints, applies
message tags and applies thinking config -- all of it operating on
anthropic.MessageParam and its unions. Splicing raw bytes means doing those
four transformations on raw JSON instead, which is what the RAW anthropic
provider already does, in its own code, today.

    SO "USE THE SDK WITHOUT ITS TYPES" AND "USE THE RAW PROVIDER" CONVERGE:
    the second implementation of those transformations already exists and is
    the one figaro ships. That is why the answer here was to prefer the raw
    provider rather than to rebuild it inside the SDK path.

## WHAT TO LOOK INTO, IF SOMEBODY RETURNS TO THIS

  1. WHETHER THE TRANSFORMATIONS CAN BE EXPRESSED ONCE. Coalescing, cache
     breakpoints and tags are provider-shaped, not SDK-shaped; if they were
     written against the wire JSON, both providers could share them and the
     SDK path would need typed values only where the vendor demands them.
  2. WHETHER THE SDK CAN STREAM A RESPONSE FOR A REQUEST IT DID NOT MARSHAL.
     Messages.NewStreaming takes params AND opts; WithRequestBody replaces the
     body, but nothing here has verified that the streaming decoder is
     indifferent to params it did not send. UNVERIFIED, and it is the first
     thing to test.
  3. WHETHER MessageParam CAN BE DECODED LAZILY. 73 allocations per message is
     the union-of-unions shape; a decoder that kept blocks as raw until a
     transformation touched them would pay for what it uses. This is a vendor
     type, so the answer is probably "no, not without a fork".

## AND THE ONE CAPABILITY THE RAW PROVIDER DOES NOT HAVE TODAY

EAGER / FINE-GRAINED TOOL INPUT STREAMING (`eager_input_streaming` on the tool
definition, form-gated) exists ONLY on the SDK path -- anthropicsdk/assemble.go
carries it and the raw provider has no mention of it. Anything else compared
came out even: thinking blocks and signatures, prompt-cache breakpoints, OAuth,
images, tool_use pairing, context limits, retry with backoff.

THE SDK PATH ALSO CARRIES TWO OPERATIONAL NICETIES the raw one does not: a
retry-cap transport, and a rate-limit note that survives the SDK discarding the
response so a Retry-After can still be reported.

So "use the raw provider instead" costs eager tool streaming unless it is
ported. It is a tool-definition field and a form opt-in, so porting it is
small -- but it is not nothing, and it should be checked before the SDK path
is retired rather than after.
