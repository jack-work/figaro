# Upgrading figaro without the ceremony

Gluck installs figaro as a nix profile entry tracking
`git+file:///home/gluck/dev/figaro-qua/.bare?ref=release`. Today an upgrade is
`figaro stop --keep-pids && nix profile upgrade --all`, run from a plain
terminal, and every pager, attended shell and `form listen` dies with the
daemon: a pager exits when its aria connection closes (`subjectDead`,
`runsession.go`). Bindings survive (`stop -k` saves them, keyed by the pane's
session leader, `angelus/bindings.go`), but each pane has to be restarted by
hand.

## One command: `figaro upgrade`

    figaro upgrade [--dry-run] [--ref <ref>]

1. **Build first, while everything runs.** `nix build` the new profile target
   (`--ref`, default the entry's own ref) and read its version from the built
   binary. Nothing is stopped if the build fails or the version is the one
   running.
2. **Plan.** Ask the running daemon for its release and protocol (`status`,
   from the version-compat lane), read the new binary's, and list every live
   figaro client process (below). Decide each one (next section).
   `--dry-run` prints the plan and stops here.
3. **Swap.** `nix profile upgrade <entry>`. Running processes keep their old
   inode; nothing breaks yet.
4. **Restart the daemon.** `stop -k` (bindings saved, hush agent kept
   unlocked), then start the new daemon by dialling it once.
5. **Clients.** Each client the plan marked *keep* reconnects on its own
   (below). Each one marked *restart* is respawned in its pane.
6. **Report.** One line per client: kept, respawned, or left alone, and why.

`figaro upgrade` runs from inside a figaro pane too: it skips its own pane in
step 5 and tells the user to re-run their command.

## Keep or restart: decided by the handshake

The rule is the CLI's own (`angelus_client.go`, `reference/compatibility.md`),
applied with the running client's release against the new daemon's:

| Client vs new daemon | Plan |
|---|---|
| same protocol, same minor, client can reconnect | keep |
| same protocol, other minor, client can reconnect | keep, warn once |
| other protocol, or either side pre-protocol (<= 0.52.3), or a dev build | restart |
| client cannot reconnect (every release up to and including this one) | restart |

A client's release comes from its executable: `/proc/<pid>/exe` resolves to a
store path whose binary answers `figaro version`. "Can reconnect" is a
capability of the client build (`cli.reconnect`), so the first release that
carries reconnect still restarts every client once; from then on a
daemon-only change keeps them.

## Reconnect in the client (new)

A pager or `form listen` whose connection closes does not exit at once. It
shows "daemon restarting", redials the same socket for up to 30 s, runs the
handshake, re-attaches to the same aria (the binding resolves it) and resumes
from the transcript position it holds. If the handshake refuses the build, it
exits with a distinct code and says "figaro was upgraded: run your command
again". A turn in flight when the daemon stops is reported as interrupted, as
now. Pending form edits follow the replica rule already in 0.53
(unconfirmed edits are reported, never silently dropped).

## Finding and respawning clients

    tmux list-panes -a -F '#{pane_id} #{pane_pid} #{pane_current_command}'

For each pane, walk the process tree under `pane_pid` to a process whose
executable is a figaro binary (by store path, not by name). Record its argv
(`/proc/<pid>/cmdline`), its cwd and environment subset (`FIGARO_*`), and
whether it is the pane's own process or a child of the pane's shell. Panes
with no figaro process are never touched. Figaro processes outside tmux
(systemd units such as telefono, scripts) are listed and left alone; units
are named so the user can restart them.

To restart a client: SIGTERM the figaro process (it restores the terminal on
the way out), wait for it to exit, then:

- child of the pane's shell: `tmux send-keys -t <pane> -l '<argv as typed>'`
  and Enter. The shell is the session leader the binding names, so `figaro`
  re-attaches to the same aria;
- the pane's own process: `tmux respawn-pane -k -t <pane> -c <cwd> <argv>`.

argv is quoted for the shell; a command line that cannot be reproduced (a
prompt read from stdin, `--stdin`) is not respawned and is reported.

## A hook, not a habit

The same plan runs from the nix side: `figaro upgrade --after-switch`
skips the build and the profile swap and does steps 2, 4, 5 and 6, so a
home-manager activation (cheroot-config) or a plain `nix profile upgrade`
followed by it gives the same result.

## Out of scope

Spain (containers restart with their unit; spain windows stay as they are),
other users' daemons, and remote troupe clients.

## Tests

- Plan logic: a table of (client release, protocol, reconnect, new daemon)
  to keep/restart, including pre-protocol and dev builds.
- Pane discovery against a fake process tree: figaro as pane process, as a
  shell child, nested under `nix develop`; non-figaro panes untouched.
- Argv quoting round-trips; `--stdin` and piped prompts are not respawned.
- Reconnect: a pager whose daemon restarts with an accepting build resumes on
  the same aria; with a refusing build it exits with the upgrade code.
- tmux, real binaries, dev root: three panes bound to three arias (one
  pager, one attended shell, one `form listen`), `figaro upgrade` to a new
  build; all three reconnected to the same arias; a non-figaro pane untouched.
