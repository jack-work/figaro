## Why big forms are slow

The pager calls `formView.Items` 2-3 times per frame, and each call:

- rebuilds the view tree by serializing the snapshot and decoding it again at every level;
- builds yank text for every row;
- formats a preview of every full value.

On a 2 MB, 16k-leaf form, one j/k takes 170-560 ms and allocates 70 MB.

## The design you steered toward (10-25)

1. One client `Replica` in place of `formMirror`, matching `~/notes/figaro/optimistic-edits-idea.md`:
   - it holds `Confirmed`, `Pending`, `Draft` and `NextSeq`;
   - the UI only ever sees `Shown`, computed from them, never edited directly;
   - a rejected edit simply drops out of `Pending`; no inverse patch is applied;
   - the server answers each request with `Applied` or `Rejected`, naming its seq.
2. The view renders `Shown` as nodes that mirror the snapshot tree. What to redraw comes from `Snapshot.Diff(prevShown, Shown)`, which skips any subtree that is the same node in both versions. The cursor holds a node, and `y` asks that node for its text. The picker renders only the visible window.
3. Server changes:
   - `{ClientID, Seq}` on sets, deltas and log records, so dedup survives a restart;
   - `LastSeq` in the response that loads a form;
   - a typed rejection code;
   - one apply rule set: today `Patch.Apply` and the tree's apply differ when an update fails, the note wants deletes applied first, and an update to a missing child dropped;
   - dots illegal in keys (your comment).

## Tests before any change

- Fuzzed patch laws: one rule set on both apply paths; merge, inverse and diff identities.
- A seeded simulator:
  - the real `store.Form` over `MemFormLog`;
  - per-connection FIFO links, whose only fault is the connection dying;
  - a server crash and restart;
  - `testing/synctest` for the debounce.
- What the simulator checks:
  - convergence;
  - one outcome per seq;
  - no lost or zombie writes, traced by unique values;
  - no flicker on a replica's own edits.
- A wire e2e, a test that counts row redraws, and tmux on the generated big forms.

## Order and what it needs from you

1. Unify the patch rules; dots become illegal in keys.
2. The wire and log changes (seq, dedup, `LastSeq`, typed rejection). This changes the on-disk record (fields added), and it is on the hot write path, so it gets benchmarks.
3. The `Replica`.
4. The view as nodes over `Shown`. This is where the speed lands: under 10 ms per keystroke and about 120 ms to open a 2 MB form.
